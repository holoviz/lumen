## 1. Issue specification

### 1.1 Observed problem

Issue #2184 states that the Anthropic provider lists only these Claude model aliases:

```text
claude-haiku-4-5
claude-sonnet-4-6
claude-opus-4-6
```

The provider does not list later Claude models. The issue says that the current request format prevents adding them.

The issue identifies two request incompatibilities:

1. Claude 4.7 and later reject a non-default `temperature` value.
2. Sonnet and Opus 5.5 reject the forced `tool_choice` generated by the current Instructor mode.

The provider default is `claude-haiku-4-5`. The issue reports that Anthropic has placed the dated Haiku 4.5 model on a retirement schedule and recommends newer Haiku, Sonnet, and Opus models.

The issue author could not test the behavior against the Anthropic API. Issue #2184 has no comments, no maintainer response, and no linked pull request at the time of this investigation.

### 1.2 Existing behavior

The local code confirms the following behavior:

1. `Anthropic.mode` defaults to `Mode.ANTHROPIC_TOOLS` (`lumen/ai/llm.py:2810`).
2. `Anthropic.model_kwargs` defines `claude-haiku-4-5` for `default` and `claude-sonnet-4-6` for `edit` (`lumen/ai/llm.py:2812-2815`).
3. `Anthropic.select_models` lists Haiku 4.5, Sonnet 4.6, and Opus 4.6 (`lumen/ai/llm.py:2819-2823`).
4. The common `Llm.temperature` parameter defaults to `0.7` and is included in client request kwargs when it is not `None` (`lumen/ai/llm.py:324-326`, `432-436`).
5. `Anthropic._client_kwargs` adds `max_tokens=1024` (`lumen/ai/llm.py:2839-2841`).
6. When a structured response is requested, `Anthropic._get_cached_client` wraps the async Anthropic client with Instructor using the selected mode (`lumen/ai/llm.py:2853-2870`).
7. The settings dialog reads `select_models` from the provider instance and can change `model_kwargs[model_type]["model"]` to the selected value (`lumen/ai/llm_dialog.py:45-110`, `373-424`). Therefore, models are automatic by default, but the UI can also allow user selection.
8. `AnthropicBedrock` inherits from `Anthropic` and has separate Bedrock model identifiers (`lumen/ai/llm.py:3095-3111`).

### 1.3 Root cause assessment

The verified root cause is a provider compatibility boundary, not only an outdated dropdown.

The request path always starts with the common temperature setting. The structured-response path always selects the provider's configured Instructor mode. The provider model list is limited because the current request format was known not to work with newer models. This behavior is documented by the source comment at `lumen/ai/llm.py:2817-2818` and by the closed model-list update PR #2118.

The exact Anthropic API rejection behavior is not independently verified in this environment. The following conclusions remain issue claims until confirmed by current Anthropic documentation or a controlled API request:

- Which current Claude models reject `temperature=0.7`.
- Whether omitting `temperature` is sufficient for each affected model.
- Which Instructor Anthropic mode avoids the rejected `tool_choice`.
- Whether Sonnet and Opus 5.5 have the same structured-output requirement.
- The present retirement status and exact Bedrock retirement IDs.

### 1.4 Intended behavior

The intended behavior is inferred from issue #2184, PR #2118, and the current provider contracts:

1. Supported current Anthropic models can be selected and invoked.
2. Each selected model receives only request parameters supported by that model.
3. Models that require the default sampling behavior do not receive a custom temperature.
4. Models that do not accept the current forced tool choice use a compatible structured-output path.
5. The default model is not an obsolete or imminently retired model unless the provider explicitly documents that choice.
6. Direct Anthropic and Anthropic Bedrock use the correct model identifiers for their respective services.
7. Existing supported models and unrelated providers keep their current behavior.
8. A rejected or unavailable model produces a clear failure and does not silently select an unrelated model.

The first six points are issue-derived requirements. Points 7 and 8 are inferred compatibility requirements from the existing provider abstraction and model-selection behavior.

If the call includes Lumen tools, `Llm.invoke` adds tool schemas at `lumen/ai/llm.py:806-813`. `Anthropic.run_client` converts those schemas at `lumen/ai/llm.py:3007-3021`. Instructor adds the schema-related structured-output behavior when `response_model` is present. These are separate tool paths and must not be conflated:

- Lumen tools are application tools used by the agent loop.
- Instructor's structured-output tool behavior is an implementation detail used to materialize a Pydantic response.

The issue specifically concerns the second path and its `tool_choice`, although a fix must preserve the first path.

### 3.4 Bedrock dependency path

```text
Llm.invoke
  -> AnthropicBedrock.get_client / inherited Anthropic methods
  -> AnthropicBedrock._create_base_client
  -> anthropic.lib.bedrock.AsyncAnthropicBedrock
  -> inherited Instructor mode and Anthropic message conversion
  -> AWS Bedrock Anthropic endpoint
```

`AnthropicBedrock` is not an independent implementation of structured output. A provider-specific change in `Anthropic` will affect it unless the subclass explicitly overrides the relevant policy. This is both a reuse benefit and a blast-radius risk.

## 4. Data and execution flow

1. The AI UI or an agent requests a model spec such as `default` or `edit`.
2. `Llm.invoke` resolves that spec through `model_kwargs`. If the spec is not explicitly configured, it falls back to `default` (`lumen/ai/llm.py:792`, `799-800`).
3. `Llm.invoke` creates common request kwargs. The current common temperature is `0.7` for Anthropic.
4. The method combines configured Lumen tools with per-call tools.
5. When a structured response is needed, `_run_tool_loop` passes `response_model` to `Anthropic.run_client`.
6. `Anthropic.run_client` converts messages and tool schemas to Anthropic format.
7. `Anthropic.get_client` resolves the concrete model ID and the configured mode.
8. `_get_cached_client` creates or reuses an Instructor wrapper for that mode.
9. The callable sends `messages.create` with the model, temperature, max tokens, tools, response model, and other request fields.
10. The external provider either returns a response or rejects an unsupported field or request shape.
11. The result is returned to the tool loop, the agent, and finally the UI.

The likely failure occurs at step 9. A 400 response prevents the agent or UI from receiving a valid structured result.

## 5. Interfaces and contracts

### Public and semi-public contracts

- `Llm.model_kwargs` maps logical model roles to provider-specific model configuration. It may contain custom keys and routing metadata. `_get_model_kwargs` removes routing-only keys before client construction (`lumen/ai/llm.py:407-423`).
- `Llm.select_models` supplies model choices to the UI. The current-model inclusion behavior allows a custom model to remain visible (`llm_dialog.py:94-110`).
- `Llm.temperature=None` means that the request must omit `temperature` (`lumen/ai/llm.py:324-326`, `432-436`).
- `Llm.mode` selects the Instructor output mode. The provider caches wrappers by mode (`lumen/ai/llm.py:482-505`).
- `Anthropic.get_client` returns a callable that accepts messages and request kwargs. `Anthropic.run_client` owns provider-specific message conversion and the final call.
- `AnthropicMixin` expects the optional `anthropic` package and maps the API key through `PROVIDER_ENV_VARS` (`lumen/ai/services.py:263-274`).
- `AnthropicBedrock` requires AWS credentials and a Bedrock-capable Anthropic SDK path. Its IDs are not interchangeable with direct Anthropic IDs.

### Compatibility constraints

1. The fix must not remove Lumen tool calls. Agent execution depends on them.
2. The fix must not change the common message schema. Many providers and agents consume it.
3. The fix must preserve streaming and non-streaming behavior. Anthropic advertises model streaming support at `lumen/ai/llm.py:2827-2829`.
4. The fix must preserve prompt caching. `Anthropic.run_client` applies cache control before the final call (`lumen/ai/llm.py:3043-3052`).
5. The fix must preserve custom `model_kwargs`. Users can override provider defaults.
6. The fix must not silently rewrite an explicit user choice unless the provider contract requires a clear compatibility error.

## 8. Open questions and stop conditions

### Internet verification addendum (2026-10-18)

Official documentation was checked after the initial repository investigation:

- Anthropic's [models overview](https://platform.claude.com/docs/en/models/overview) lists `claude-haiku-5-5`, `claude-sonnet-5-5`, and `claude-opus-5-5` as current Claude API IDs. It also lists their Bedrock base IDs as `anthropic.claude-haiku-5-5`, `anthropic.claude-sonnet-5-5`, and `anthropic.claude-opus-5-5`.
- Anthropic's [model deprecations page](https://platform.claude.com/docs/en/about-claude/model-deprecations) confirms that `temperature`, `top_p`, and `top_k` are deprecated for Claude 4.7 and later, and that a non-default value returns HTTP 400. The page still marks `claude-haiku-4-5-20251001` as active with a tentative retirement date of not sooner than October 15, 2026. A tentative date does not prove that the model is retired on the investigation date.
- Anthropic's [structured outputs documentation](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) documents native JSON outputs through `output_config.format` and strict tool use through `strict: true`. This is evidence that a native JSON-output path exists, but it does not prove that Lumen can use it without an adapter change.
- Instructor's [Anthropic integration documentation](https://github.com/567-labs/instructor/blob/main/docs/integrations/anthropic.md) says that ordinary `Mode.TOOLS` uses Anthropic tools and forces a single tool for a normal response model. It changes tool choice automatically when `thinking` is enabled. This supports the issue's concern about forced tool choice, but it does not independently prove that every Sonnet or Opus 5.5 request fails.
- AWS's [Anthropic Bedrock model cards](https://docs.aws.amazon.com/bedrock/latest/userguide/model-cards-anthropic.html) list Haiku 5.5, Sonnet 5.5, and Opus 5.5. Anthropic's [Bedrock documentation](https://platform.claude.com/docs/en/build-with-claude/claude-on-amazon-bedrock-legacy) states that newer models may require a cross-region inference-profile ID instead of the base model ID.

This changes the evidence status: the temperature requirement and the availability of newer model families are now externally confirmed. The exact Lumen-compatible Instructor mode, final Bedrock profile IDs for the deployment region, and successful end-to-end requests remain unresolved. A live API test or a small isolated provider experiment is still required before selecting the final production design.

Implementation should stop for maintainer clarification or provider verification when any of these questions remains unanswered:

1. What exact direct Anthropic model IDs should replace or supplement the current aliases?
2. Should the default be `claude-haiku-5-5`, another current model, or a repository-configured alias?
3. What exact Instructor mode works for each target model?
4. Does the compatible mode preserve both structured output and Lumen-native tool calls?
5. Should compatibility be selected by model family, by explicit `mode` in `model_kwargs`, or by a bounded retry after a typed provider error?
6. What exact Bedrock inference-profile IDs should be used in each AWS region?
7. Should the UI expose a temperature control for models that require omission, or should the provider keep the setting internally disabled?
8. What is the accepted fallback when the configured default model is retired?

Stop implementation if:

- A target model cannot be verified as available.
- The selected Instructor mode cannot preserve the required structured-output and tool contracts.
- The required behavior needs a change to the common `Llm` abstraction that affects unrelated providers without a complete regression plan.
- The baseline AI test suite cannot be distinguished from an environment or dependency failure.
- A maintainer decision is needed about the default model or public model list.

## 9. Minimum coherent change surface

The smallest justified scope is provider-local:

1. Add an explicit Anthropic model-compatibility policy near `Anthropic`, or encode compatibility in each `model_kwargs` entry.
2. Use that policy to omit temperature only for confirmed affected models.
3. Select the confirmed structured-output mode per affected model, without changing unrelated providers.
4. Apply the same policy to `AnthropicBedrock` with separate IDs.
5. Add deterministic request-shape tests and live-verification notes.

Do not begin with a broad change to `Llm._client_kwargs`, `Llm._run_tool_loop`, or `Llm._create_instructor_client`. The evidence does not show that those shared abstractions are defective. The issue is at the Anthropic provider integration boundary.

## Handoff summary

Issue #2184 is a model-compatibility problem in `lumen/ai/llm.py`. The provider currently selects older Claude defaults, sends the common `temperature=0.7`, and uses `Mode.ANTHROPIC_TOOLS` for structured responses. The issue claims that newer Claude models reject the temperature and forced Instructor tool choice. The code confirms where those values enter the request, but live provider behavior is not yet verified.

The next engineer must first confirm the current direct Anthropic and Bedrock model IDs and the valid Instructor mode for each target model. Then implement a provider-local, model-aware policy. Add request-shape tests before changing defaults. Test direct Anthropic and Bedrock separately. Verify tool loops, structured output, caching, streaming, model selection, and old-model compatibility. Do not claim complete resolution without live-provider evidence or a precise statement of the remaining external verification limitation.
